## 📝 Summary

I'm a postgraduate Data Science & IoT specialist (MCA) who builds complete, production-grade AI systems rather than standalone notebooks. My work spans the full lifecycle of a model: **data collection → statistical analysis → feature engineering → model development → experiment tracking → deployment → monitoring → iteration.**

I care about three things in every system I build:

- **Accuracy** — the model needs to actually work on data it hasn't seen
- **Interpretability** — stakeholders need to understand *why* a model made a decision, not just trust a black box
- **Deployability** — a model sitting in a Jupyter notebook creates zero business value; it has to ship

That philosophy shows up across my project history: fraud detection systems with SHAP-based explainability, delivery-delay models wrapped in monitored APIs, IoT sensor pipelines feeding directly into ML inference, and a multi-tenant SaaS risk platform built with production concerns (A/B testing, feature stores, monitoring) from day one.

## 🚀 Featured Projects

### 🏗️ [SaaS AI Risk Platform](https://github.com/Ashwani4545/saas-ai-risk-platform)
A multi-tenant machine learning platform designed for production risk-prediction workloads, not just a single model demo.

- **Architecture**: Multi-tenant design so multiple client organizations can run isolated risk models on shared infrastructure
- **Feature Store**: Centralized, reusable feature definitions to eliminate training/serving skew
- **Vector Similarity Search**: Enables similarity-based risk lookups and nearest-neighbor comparisons
- **A/B Testing**: Built-in experimentation framework to compare model versions under live traffic
- **Monitoring**: Comprehensive tracking of model performance and data drift over time

`Python` `MLOps` `Vector Search` `A/B Testing` `Multi-tenancy`

---

### 📦 [E-Commerce Delivery Prediction](https://github.com/Ashwani4545/E-CommerceProductDeliveryPrediction)
An end-to-end ML system that predicts delivery delays for e-commerce orders, built as a full pipeline rather than a model file.

- **Modeling**: Gradient-boosted models (LightGBM, XGBoost) tuned for delay classification
- **Explainability**: SHAP values expose which features drive each individual prediction, making the model auditable by non-technical stakeholders
- **MLOps**: MLflow for experiment tracking, DVC for dataset/model versioning
- **Deployment**: FastAPI backend serving predictions, Streamlit front-end for interactive use, containerized with Docker
- **CI/CD**: GitHub Actions automate testing and deployment
- **Business Layer**: Power BI dashboard translating model output into operational insight

`LightGBM` `XGBoost` `MLflow` `DVC` `FastAPI` `Streamlit` `Docker` `SHAP` `Power BI`

## 🏛️ Engineering Approach

Every project follows the same underlying discipline, regardless of domain:

```
Raw Data
   │
   ▼
Data Engineering  ──►  cleaning, validation, pipeline design
   │
   ▼
Feature Engineering  ──►  domain-informed, leakage-checked
   │
   ▼
Model Development  ──►  baseline → iteration → explainability
   │
   ▼
Experiment Tracking  ──►  MLflow runs, versioned datasets (DVC)
   │
   ▼
Model Registry  ──►  reproducible, versioned artifacts
   │
   ▼
API / Application Layer  ──►  FastAPI / Streamlit, containerized
   │
   ▼
Dashboard  ──►  Power BI / Tableau for stakeholder visibility
   │
   ▼
Monitoring  ──►  drift detection, performance tracking, feedback loop
```

The goal is always to move from **"training a model"** to **engineering a complete, monitored system** — one that keeps working, and keeps being trusted, after the initial deployment.
